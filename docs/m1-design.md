# M1: the 3DS boot payload (`ios3ds.firm`)

## Who does what

```
 Luma3DS chainloader  ──►  ARM9 monitor (ARM9 RAM 0x08000040)      ARM11 stub (AXI WRAM 0x1FF90000)
                           ├ consoles on both screens              ├ CP15 ID registers → mailbox
                           ├ sd:/ios3ds/log.txt (synced per line)  ├ VFP on (CPACR + FPEXC)
                           ├ handshake with the ARM11 ◄────────────┤ ready loop (heartbeat, token echo)
                           ├ boot.cfg, kernel.bin, devtree.bin,    ├ on PROB: instruction probes
                           │  shim.bin → FCRAM                     └ on JUMP: r0=boot_args, bx entry
                           ├ builds boot_args                           │
                           ├ JUMP ─────────────────────────────────────►│ XNU (MMU off, ARM state)
                           └ monitor loop: ARM11 ring + XNU ring ──► screen + SD
```

The ARM9 does all I/O and stays alive forever, so a dead ARM11 or a hung
kernel still leaves a log behind.
- Both CPUs run with caches and MPU/MMU **off** until XNU takes over the ARM11.
- All shared buffers are therefore coherent without any cache maintenance.
- Under XNU, the shim cleans each cache line it writes.

Core 1 is never touched; it stays parked in boot11. VFP is enabled before the jump.

## Memory map used by ios3ds

| Range | Owner | Content |
|---|---|---|
| 0x08000000–0x0800003F | ARM9 | exception veneers (boot9 jumps here) |
| 0x08000040–0x080FFFFF | ARM9 | monitor code and data, stack top 0x08100000 |
| 0x18000000–0x182FFFFF | XNU | `/vram` (reserved for the XNU framebuffer in M4) |
| 0x18300000–0x1848CA00 | Luma/ARM9 | framebuffers from Luma's screen init (BGR8) |
| 0x1FF90000–0x1FF9FFFF | ARM11 | stub code and stacks |
| 0x1FFA0000–0x1FFAFFFF | XNU | `/pram` (persistent panic log, magic 'OOPS') |
| 0x1FFF0000–0x1FFF13FF | both | mailbox `shared_t` (boot/common/ios3ds.h) |
| 0x1FFFFFA0–0x1FFFFFCF | boot11 | RAM exception vectors (borrowed during probes, then restored) |
| 0x20000000 | XNU | physBase = VA 0x80000000 |
| 0x20001000–0x2081AFFF | XNU | kernelcache, flat image (`kernel.bin`, patched) |
| 0x2081B000 | XNU | device tree (`devtree.bin`, 38,940 B) |
| 0x20825000 | XNU | boot_args (the same offset real iBoot uses: 0x08825000) |
| 0x20826000 | XNU | `shim.bin` (16 KiB slot) |
| 0x2082A000 | XNU→ARM9 | log ring: 16 B header + 256 KiB buffer |
| 0x20900000 | XNU | topOfKernelData; the kernel builds its page tables here |
| …0x27FFFFFF | XNU | free RAM (memSize = 128 MiB) |

These addresses are generated by `scripts/mkboot.py` and written to `boot.cfg`.
The ARM9 checks every rule the kernel imposes before it jumps:
- physBase is 16 MB aligned;
- memSize is a multiple of 1 MB;
- `top_pa` is 16 KB aligned;
- all regions are in order.

## Mailbox protocol (`shared_t` at 0x1FFF0000)

1. The ARM11 starts first, since Luma releases it before the ARM9. It clears
   the mailbox (keeping `a9_token`), fills in the ID registers, enables VFP,
   sets `magic` and `stage=READY`, then loops writing `a11_echo = a9_token`.
2. The ARM9 writes a fresh token (old + 1) and trusts the mailbox only once
   the token is echoed. That rules out stale contents left by a previous boot.
3. `a9_cmd = PROB`: the ARM11 runs the instruction probes with its own
   exception stubs installed in the boot11 RAM vectors, then restores them.
   If it hangs, the ARM9 names the probe, and `probes=0` in `boot.cfg` skips them.
4. `a9_cmd = JUMP` with `jump_pc` and `jump_r0`: the ARM11 acks, invalidates
   its caches and TLB, and jumps.
5. Logs: the ARM11 writes to `log_buf`/`log_head`, and XNU writes to the FCRAM
   ring through the shim. The ARM9 drains both to the screen and to `log.txt`.

## `sd:/ios3ds/boot.cfg`

`boot.cfg` holds `key=value` lines; `#` starts a comment. It is generated by
`make sd` and is safe to edit on the card.

| Key | Meaning |
|---|---|
| `cmdline` | XNU boot-args (default `debug=0x8 serial=1 amfi_allow_any_signature=1 cs_enforcement_disable=1`) |
| `jump` | `0` = load everything but don't start XNU |
| `boot_delay` (old name `countdown_ms`) | grace period before the jump, in ms (default 1000); **A** skips it, **B** cancels the jump |
| `probes` | `0` = skip the ARM11 instruction probes |
| `ba_version`, `ba_revision` | boot_args header. **4.2.1 needs version 5** (or it panics "Epoch Mismatch") |
| `kernel`, `devtree`, `shim` | file paths |
| `kernel_pa` … `top_pa` | layout, as generated |
| `video_*` | Boot_Video handed to XNU. All 0 for now; used in M4 |

## What appears on the screens

- **Top:** the scrolling log, the same text as `log.txt`.
  - green = ok, yellow = warning, red = error, cyan = ARM11 messages
  - white after the jump = XNU's own console output
- **Bottom:** the version string, SD/ARM11 status lines, the countdown, and a
  "monitor alive #N" counter that keeps rising while the ARM9 is alive.

## Failure modes, each with a visible message

| Situation | What you see |
|---|---|
| Luma didn't initialise the screens | black screens; `log.txt` says "no framebuffers from loader" |
| SD not mounted | red "SD MOUNT FAILED" plus the FatFs error code |
| ARM11 never reaches READY | "ARM11 STUCK at stage …", with stage, probe, magic and echo values |
| ARM11 hangs in a probe | "ARM11 HUNG IN PROBE n (encoding …)"; set `probes=0` |
| boot.cfg missing or invalid | the reason, then the monitor keeps running |
| kernel/devtree/shim missing or too big | load error with the FatFs code |
| XNU starts | "[monitor] XNU entry stub ran: L1[0x800] = …". This proves the entry stub built its page tables |
| XNU prints or panics | the text appears in white on the top screen and in `log.txt` |
